# Frank!Gateway

Frank!Gateway is [Apache APISIX](https://apisix.apache.org/) with the WeAreFrank plugins for SOAP, FSC and OIDC.
This chart runs it in **standalone mode**: routes are read from a file, there is no etcd and no Admin API.

[Frank!Gateway source on GitHub](https://github.com/wearefrank/frank-gateway)

## Usage

[Helm](https://helm.sh) must be installed to use the charts.
Please refer to Helm's [documentation](https://helm.sh/docs) to get started.

Once Helm has been set up correctly, add the repo as follows:

```shell
helm repo add wearefrank https://wearefrank.github.io/charts
```

If you had already added this repo earlier, run `helm repo update` to retrieve
the latest versions of the packages.  You can then run `helm search repo
wearefrank` to see the charts.

To install the Frank!Gateway chart:

```shell
helm install frank-gateway wearefrank/frank-gateway
```

To uninstall the chart:

```shell
helm delete frank-gateway
```

## How it works

- The chart renders two files: the APISIX `config.yaml` (from `config`) and the routes file `apisix.yaml` (from `standalone`).
- `config` uses the native APISIX names and structure. Only the keys that differ from the APISIX defaults are needed. The chart manages the listen ports, the deployment mode, the Admin API, the Control API and the Prometheus export itself.
- The container runs as a non-root user with a read-only root filesystem, no capabilities and the `RuntimeDefault` seccomp profile. APISIX needs to write to a few paths, so the chart mounts `emptyDir` volumes there. An init container copies the image's `conf` directory into the writable volume and links `apisix.yaml` into it. You do not have to do anything for this.
- Everything that exists in Kubernetes has the same name and structure as in Kubernetes: `env`, `envFrom`, `volumes`, `volumeMounts`, `resources`, `podSecurityContext`, `securityContext`, `service.ports`, `ingress.rules`, `ingress.tls`, `httpRoute.parentRefs`, and so on.
- Mistakes in the values fail `helm template` and `helm install` with a clear message, for example a route without `parentRefs`, a ServiceMonitor without metrics, clashing ports or an `image.repository` that still contains the registry host. All problems are reported at once.

### Overriding defaults

Maps are merged with the defaults and lists are replaced as a whole. To remove a default entry of a map, set it to `null`:

```yaml
config:
  nginx_config:
    http:
      custom_lua_shared_dict:
        jwt-client-cache: null   # the other shared dictionaries stay
```

For a list, such as `config.plugins` or `service.ports`, repeat all the entries you want to keep.

### Templates in values

Values marked as template in the parameter tables can contain Helm templates, so you can use the release name or namespace in them:

```yaml
ingress:
  rules:
    - host: "{{ .Release.Name }}.example.nl"
env:
  - name: ENVIRONMENT
    value: "{{ .Release.Namespace }}"
```

`standalone.apisixYaml` and `config` are never rendered as templates, their `${{NAME}}` placeholders are for APISIX.

### Common labels and annotations

`commonLabels` and `commonAnnotations` are added to all resources, and `commonAnnotations` also to the pods. The standard `app.kubernetes.io` labels cannot be overridden, and the annotations of a resource win over `commonAnnotations`.

## Routes

Put the routes in `standalone.apisixYaml`. The `#END` marker that APISIX requires at the end of the file is added by the chart.

```yaml
standalone:
  apisixYaml: |
    upstreams:
      - id: my-backend
        nodes:
          "my-backend.my-namespace.svc.cluster.local:80": 1
    routes:
      - id: my-route
        uri: /my-api/*
        upstream_id: my-backend
```

Use `${{NAME}}` placeholders for secrets and feed them from the environment, for example certificates:

```yaml
env:
  - name: TLS_CERT
    valueFrom:
      secretKeyRef:
        name: frank-gateway-cert
        key: tls.crt
  - name: TLS_KEY
    valueFrom:
      secretKeyRef:
        name: frank-gateway-cert
        key: tls.key
standalone:
  apisixYaml: |
    ssls:
      - cert: ${{TLS_CERT}}
        key: ${{TLS_KEY}}
        snis:
          - api.example.nl
```

To keep the routes in your own ConfigMap or Secret (for example generated by Kustomize), set `standalone.existingConfigMap` or `standalone.existingSecret`. The file must be named `apisix.yaml` (or set `standalone.key`) and end with `#END`. APISIX reloads the file by itself when it changes, the pods are not restarted.

### Secrets

Do not put secrets in `standalone.apisixYaml` or `config`: they end up in a ConfigMap, which anyone who can read ConfigMaps in the namespace can read. This includes the keys of consumers (`key-auth`, `basic-auth`, `jwt-auth`), client secrets of `openid-connect` and private keys. Use one of these instead:

- A `${{NAME}}` placeholder that APISIX resolves from an environment variable, filled by `env` or `envFrom` from a Secret, as in the example above. The same works in `config`.
- `standalone.existingSecret`, with the complete `apisix.yaml` in a Secret, for example a SealedSecret.

The resolved value of a placeholder is what APISIX holds in memory. Keep that in mind when you enable the Control API, see below.

## Exposing the gateway

Choose one or more of the following. They all send traffic to the gateway Service.

### Service of type LoadBalancer

```yaml
service:
  type: LoadBalancer
  externalTrafficPolicy: Local
  annotations:
    lbipam.cilium.io/ips: 10.0.0.10
```

### Ingress

Same structure as the Kubernetes Ingress. A path without `backend` goes to the gateway Service, on the port in `ingress.defaultBackendPort` (`https` by default). This example passes TLS through to APISIX with Cilium, so APISIX can validate client certificates:

```yaml
ingress:
  enabled: true
  ingressClassName: cilium
  annotations:
    ingress.cilium.io/tls-passthrough: "enabled"
  rules:
    - host: api.example.nl
      http:
        paths:
          - path: /
            pathType: Prefix
```

### Gateway API

Use an `HTTPRoute` when the Gateway terminates TLS, the traffic then goes to the `http` port (`httpRoute.defaultBackendPort`). Use a `TLSRoute` for TLS passthrough, the traffic then goes to the `https` port, so APISIX terminates TLS and can validate client certificates.

```yaml
httpRoute:
  enabled: true
  parentRefs:
    - name: shared-gateway
      namespace: gateways
      sectionName: https
  hostnames:
    - api.example.nl

tlsRoute:
  enabled: true
  parentRefs:
    - name: shared-gateway
      namespace: gateways
      sectionName: tls-passthrough
  hostnames:
    - api.example.nl
```

A `TLSRoute` uses `gateway.networking.k8s.io/v1` when the cluster has it and `v1alpha2` otherwise. Set `tlsRoute.apiVersion` to choose one yourself.

## Control API

The Control API (health checks, plugin and upstream status) is disabled by default. When enabled, it is reachable through its own Service `<release>-frank-gateway-control`. It is never exposed through the Ingress or the Gateway API routes.

It has no authentication, and it is more than a status page: it returns the route configuration, which can include values resolved from `${{NAME}}` placeholders, and `PUT /v1/plugins/reload` reloads the plugins of the running gateway. Restrict access to it with the `networkPolicy` below.

```yaml
control:
  enabled: true
```

## Network policy

An optional NetworkPolicy (`networkPolicy.enabled`) that only restricts ingress, because the gateway has to reach its upstreams. The gateway ports accept traffic from anywhere, so Ingress controllers and Gateways keep working. The Control API and metrics ports are only reachable from the peers you list. Without peers, nobody can reach them. A peer has the structure of `from` in a NetworkPolicy ingress rule:

```yaml
networkPolicy:
  enabled: true
  control:
    from:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: dashboard
        podSelector:
          matchLabels:
            app.kubernetes.io/name: frank-gateway-dashboard
  metrics:
    from:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: monitoring
```

Use `networkPolicy.extraIngress` for other rules. Whether the policy is enforced depends on your network plugin.

## Metrics

```yaml
metrics:
  enabled: true
  serviceMonitor:
    enabled: true   # needs the Prometheus Operator CRDs
```

The `prometheus` plugin is in the default plugin list. Enable it on routes or in a `global_rules` entry in `apisix.yaml`:

```yaml
standalone:
  apisixYaml: |
    global_rules:
      - id: prometheus
        plugins:
          prometheus: {}
```

## Image

The image is `<image.registry>/<image.repository>:<image.tag>`, and the tag defaults to the chart `appVersion`. To use a mirror, set `image.registry`. To pin the image, set `image.digest`, which takes precedence over the tag:

```yaml
image:
  registry: registry.example.nl
  repository: wearefrank/frank-gateway
  digest: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

## Availability and shutdown

- The pods are spread over the nodes when possible (`topologySpreadConstraints`, with the selector filled in for you). Set it to `[]` to turn that off. `podDisruptionBudget` and `autoscaling` are available as well.
- On shutdown the `preStop` hook waits 10 seconds so Kubernetes can stop sending traffic while the gateway keeps serving, then stops nginx gracefully and waits until the in-flight requests have finished. `config.nginx_config.worker_shutdown_timeout` (45s) must stay below `terminationGracePeriodSeconds` (60s) minus that 10 seconds, otherwise Kubernetes kills the container first. If you change one, change the other.

## Troubleshooting

With a read-only root filesystem it is hard to debug a container that stops right after it starts. Enable the diagnostic mode, which only sleeps, without probes, so you can open a shell:

```shell
helm upgrade frank-gateway wearefrank/frank-gateway --reuse-values --set diagnosticMode.enabled=true
kubectl exec -it deploy/frank-gateway -- sh
/docker-entrypoint.sh docker-start   # start the gateway by hand and read its output
```

## Client addresses and allow lists

Plugins such as `ip-restriction` use the address of the client as APISIX sees it. What APISIX sees depends on how traffic comes in. The end-to-end tests check each of these:

| Way in | The gateway sees | What to set |
| --- | --- | --- |
| `LoadBalancer` Service | the client address with `externalTrafficPolicy: Local`, with MetalLB in layer 2 mode and in BGP mode. With the default `Cluster` it sees the address of a node. With BGP and `Local`, only the nodes that run the gateway announce the address. | `service.externalTrafficPolicy: Local` |
| Ingress that terminates TLS | the client address from `X-Forwarded-For` | `config.nginx_config.http.real_ip_header: X-Forwarded-For`, `real_ip_recursive: "on"` and `real_ip_from` with the network of the controller pods |
| `HTTPRoute` | the same, from `X-Forwarded-For`. The Service of the Gateway needs `externalTrafficPolicy: Local` as well. | as for an Ingress that terminates TLS |
| Ingress with TLS passthrough | depends on the controller. A proxy that opens a new connection to the gateway shows its own address, as HAProxy did in the tests, unless it sends the PROXY protocol. A controller that keeps the original source address shows the client. | for a proxy that shows its own address, see below |
| `TLSRoute` | with Envoy Gateway, the address of the proxy, also with `externalTrafficPolicy: Local`. Other implementations may differ. | filter on the client certificate instead, or check your implementation |

`externalTrafficPolicy: Local` only keeps the client address between the load balancer and the proxy in front of the gateway. It does not change the connection from that proxy to the gateway. To find out what your setup does, send a request through it and look at the address in the access log of the gateway, or call a route with the `serverless-post-function` plugin that returns `$remote_addr`.

The `real_ip_from` network must only contain the addresses of the proxy in front of the gateway. Any address in it can pretend to be any client.

For TLS passthrough with an Ingress controller that can send the PROXY protocol, such as HAProxy, let APISIX listen on an extra port that expects it, and send traffic to that port. The extra port is not a container port that the chart knows, so add it to `service.ports` with a number as `targetPort`:

```yaml
service:
  ports:
    - name: http
      port: 80
    - name: https
      port: 443
    - name: https-pp          # at most 15 characters, an Ingress needs that
      port: 444
      targetPort: 9444
config:
  apisix:
    proxy_protocol:
      listen_https_port: 9444
  nginx_config:
    http:
      real_ip_header: proxy_protocol
      real_ip_from:
        - 10.244.0.0/16       # the pod network of your cluster
ingress:
  enabled: true
  ingressClassName: haproxy
  defaultBackendPort: https-pp
  annotations:              # these annotations are the ones of HAProxy, other controllers have their own
    haproxy.org/ssl-passthrough: "true"
    haproxy.org/send-proxy-protocol: proxy-v2
```

The NetworkPolicy of the chart only opens the gateway ports, so with `networkPolicy.enabled` add the extra port to `networkPolicy.extraIngress`.

## Migrating from version 0.x

Version 1.0.0 is not a wrapper around the Apache APISIX chart anymore, so the values changed:

| 0.x                                                                  | 1.0.0                                                                        |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `frankgateway.image.repository` and `tag`                            | `image.registry` (`ghcr.io`), `image.repository` (`wearefrank/frank-gateway`) and `image.tag` |
| `frankgateway.apisix.deployment.standalone.config`                   | `standalone.apisixYaml`                                                      |
| `frankgateway.apisix.deployment.standalone.existingConfigMap`        | `standalone.existingConfigMap`                                               |
| `frankgateway.apisix.plugins` and `customPlugins`                    | `config.plugins` (custom plugins are baked in the image, list them as well)  |
| `frankgateway.apisix.ssl.sslProtocols` and `sslCiphers`              | `config.apisix.ssl.ssl_protocols` and `ssl_ciphers`                          |
| `frankgateway.apisix.nginx.customLuaSharedDicts`                     | `config.nginx_config.http.custom_lua_shared_dict`                            |
| `frankgateway.extraEnvVars`                                          | `env`                                                                        |
| `frankgateway.extraVolumes` and `extraVolumeMounts`                  | `volumes` and `volumeMounts`                                                 |
| `frankgateway.ingress.hosts` and `servicePort`                       | `ingress.rules` and `ingress.defaultBackendPort`                             |
| `frankgateway.etcd.*`, `externalEtcd.*`, `ingress-controller.*`      | removed, there is no etcd and no ingress controller                          |
| `frankgateway.apisix.admin.*`, `frankgateway.apisix.prometheus.*`    | removed (Admin API), `metrics.*`                                             |

The `securityContext` and `podSecurityContext` defaults no longer need to be set. Remove `readOnlyRootFilesystem: false` workarounds, the chart supports a read-only root filesystem. Resource names changed too, the Deployment is now called `<release>-frank-gateway`. The registry host is no longer part of `image.repository`, an old value such as `ghcr.io/wearefrank/frank-gateway` fails with a message that tells you to set `image.registry`.

## Parameters

### General

Frank!Gateway: Apache APISIX in standalone (file-driven) mode with the WeAreFrank plugins.
There is no etcd and no Admin API. Routes are read from an `apisix.yaml` file, see `standalone`.

Naming follows the Kubernetes manifests where possible: `env`, `volumes`, `ingress.rules`,
`httpRoute.parentRefs`, `service.ports` and so on have the same structure as the Kubernetes field.

Values marked as template can contain Helm templates, for example `{{ .Release.Name }}`
or `{{ .Release.Namespace }}`. This is not the case for `standalone.apisixYaml` and `config`: their
`${{NAME}}` placeholders are for APISIX, which resolves them from the environment.

### Standalone configuration (apisix.yaml)

In standalone mode APISIX reads its routes, upstreams, ssls, consumers and so on from `apisix.yaml`.
The chart adds the mandatory `#END` marker when it is missing from `standalone.apisixYaml`.
`${{NAME}}` placeholders in the file are resolved by APISIX from environment variables, so secrets
can be injected with `env` or `envFrom` and do not have to be stored in the file.
When `existingConfigMap` or `existingSecret` is used, APISIX reloads the file when Kubernetes updates it
(the pod does not restart). With `apisixYaml` the pod restarts on every change.

| Name                           | Description                                                                                                 | Value         |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------- | ------------- |
| `standalone.apisixYaml`        | Content of `apisix.yaml`, ignored when `existingConfigMap` or `existingSecret` is set                       | `routes: []
` |
| `standalone.existingConfigMap` | Name of an existing ConfigMap that contains the `apisix.yaml` file                                          | `""`          |
| `standalone.existingSecret`    | Name of an existing Secret that contains the `apisix.yaml` file (takes precedence over `existingConfigMap`) | `""`          |
| `standalone.key`               | Key of the `apisix.yaml` file in the ConfigMap or Secret                                                    | `apisix.yaml` |

### APISIX configuration (config.yaml)

`config` is the content of the APISIX `config.yaml`, using the native APISIX names (snake_case).
See https://apisix.apache.org/docs/apisix/configuration/. It is merged over the APISIX defaults, so only
the values that differ need to be set. Lists, such as `plugins`, are replaced as a whole.

The chart manages these keys itself and overrides them: `apisix.node_listen`, `apisix.enable_admin`,
`apisix.enable_control`, `apisix.control`, `apisix.ssl.enable`, `apisix.ssl.listen`, `deployment`
and `plugin_attr.prometheus` (see `containerPorts`, `control` and `metrics`).

### Diagnostic mode

With a read-only root filesystem you cannot easily debug a container that crashes on start. In diagnostic
mode the gateway container only runs `sleep infinity`, without probes and without `lifecycle` hooks, so
you can open a shell in it. The init container still runs, so the `conf` directory is prepared.

| Name                     | Description                                 | Value          |
| ------------------------ | ------------------------------------------- | -------------- |
| `diagnosticMode.enabled` | Enable diagnostic mode                      | `false`        |
| `diagnosticMode.command` | Command to run in diagnostic mode           | `["sleep"]`    |
| `diagnosticMode.args`    | Arguments of the command in diagnostic mode | `["infinity"]` |

### Network policy

An optional NetworkPolicy for the gateway pods. It only restricts ingress, the gateway has to reach its upstreams.
The gateway ports (`containerPorts.http` and `containerPorts.https`) accept traffic from anywhere, so ingress
controllers and Gateways keep working. The Control API and metrics ports are only reachable from the
peers you list in `control.from` and `metrics.from`. Without peers nobody can reach them.
A peer has the structure of `from` in a NetworkPolicy ingress rule, for example a `podSelector`,
a `namespaceSelector` or an `ipBlock`.

| Name                         | Description                                                                              | Value   |
| ---------------------------- | ---------------------------------------------------------------------------------------- | ------- |
| `networkPolicy.enabled`      | Create a NetworkPolicy                                                                   | `false` |
| `networkPolicy.control.from` | Peers that may reach the Control API port (template). Needs `control.enabled`.           | `[]`    |
| `networkPolicy.metrics.from` | Peers that may reach the metrics port (template). Needs `metrics.enabled`.               | `[]`    |
| `networkPolicy.extraIngress` | Additional ingress rules, same structure as `spec.ingress` in a NetworkPolicy (template) | `[]`    |
